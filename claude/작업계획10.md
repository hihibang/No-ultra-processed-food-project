## 1. 비교 실행 후 비교함 자동 비우기

### 관련 파일
- `front/src/pages/ComparePage.jsx` : `handleRunCompare`, `savedResult`, `<ComparisonResultModal />` 렌더링
- `front/src/contexts/CompareContext.jsx` : `clearCompare` (약 50행)
- `front/src/hooks/useCompare.js` : `runCompare`, `clearCompare` 노출 여부 확인
- `front/src/api/comparisonApi.js` : `create` (`POST /api/comparisons`)

### 작업 내용
1. `handleRunCompare`에서 `runCompare()` 성공 후 `setSavedResult(result)`와 함께 `clearCompare()`를 호출한다.
2. **주의(중요)**: `ComparePage.jsx`는 `compareItems.length === 0`이면 빈 화면을 먼저 `return`한다.
   비우기 직후 빈 화면 분기로 떨어지면 `<ComparisonResultModal />`이 unmount되어 모달이 열리자마자 닫힌다.
   아래 중 하나로 처리한다.
   - (권장) 모달 렌더링을 빈 화면 분기보다 위로 올려, `savedResult`가 있으면 `compareItems` 상태와 무관하게 모달이 유지되도록 한다.
   - 또는 `clearCompare()`를 모달 닫힘(`onClose`) 시점으로 미룬다.
3. 모달 닫힘 시 `savedResult`를 `null`로 초기화하는지 확인한다.
4. 실패(catch) 경로에서는 `clearCompare()`를 호출하지 않는다.

### 확인 항목
- 비교 실행 성공 → 모달 열림 → 비교함 비워짐 (모달은 유지되어야 함)
- 모달 닫은 후 `/compare`가 빈 비교함 상태로 정상 표시
- 비교 실패 시 비교함이 그대로 유지됨

## 2. 상품 목록(`Catalog.jsx`) 중복 노출 해결

> 참고: 실제 파일명은 `front/src/pages/CatalogPage.jsx`이다. 요청의 `Catalog.jsx`는 이 파일을 가리키는 것으로 본다.

### 관련 파일
- `front/src/pages/CatalogPage.jsx` : 목록 상태 관리, 데이터 합치는 로직(약 189~199행 `...prev` 부근)
- `front/src/data/CatalogPage.data.js`
- `server/routes/food_routes.py` : `GET /api/foods`
- `server/models/food_model.py` : 목록 조회 쿼리 (`active_food_catalog` 대상, 현재 `ORDER BY`/`LIMIT`/`OFFSET` 및 중복 방지 조건 확인 필요)
- `server/food_db.sql` : `active_food_catalog` 정의 및 `report_no` PK 여부 확인

### 원인 점검 순서
1. **백엔드**
   - 페이지네이션(`LIMIT`/`OFFSET`) 사용 시 `ORDER BY`가 없거나 동점 값이 많으면 페이지 간 중복이 발생한다.
     정렬 키 끝에 고유 키(`report_no`)를 추가해 정렬을 안정화한다.
   - 조인 등으로 같은 `report_no`가 여러 행으로 나오는지 확인하고, 필요하면 `DISTINCT` 또는 `GROUP BY report_no`를 적용한다.
   - 응답 건수와 `report_no` 고유 개수를 비교해 실제 중복 여부를 먼저 확인한다.
2. **프론트엔드**
   - 무한 스크롤/더보기에서 `[...prev, ...next]`로 합치는 부분에 `report_no` 기준 중복 제거를 추가한다.
     예: `const seen = new Set(); ... filter(item => !seen.has(item.report_no) && seen.add(item.report_no))` 형태, 또는 `Map` 사용.
   - 필터/카테고리 변경 시 기존 목록을 초기화한 뒤 합치는지 확인한다(이전 필터 결과가 섞이는 중복 방지).
   - React StrictMode나 중복 `fetch` 호출로 같은 페이지가 두 번 합쳐지는지 확인한다.

### 확인 항목
- 스크롤/더보기를 여러 번 해도 동일 `report_no`가 두 번 보이지 않음
- 필터 변경 후 목록이 올바르게 초기화됨
- 백엔드 응답의 `report_no` 고유 개수 = 목록 항목 수

## 3. 비교 결과 모달에 [탄수화물] 항목 추가

### 관련 파일
- `front/src/pages/Comparison/ComparisonResultModal.jsx` : `NUTRITION_ROWS` (약 26~32행)
- `server/utils/comparison_report.py` : `nutrition` 객체 (`"carbohydrate"` 키 이미 포함됨)
- `server/models/comparison_model.py` : 조회 컬럼에 `carbohydrate` 포함 여부 (약 66행, 이미 포함으로 보임)
- `server/food_db.sql` : `food_nutrition.carbohydrate` (DECIMAL(8,2), 탄수화물(g))
- `server/schemas/food_schema.py` : `carbohydrate` 필드 (이미 존재)

### 작업 내용
1. `NUTRITION_ROWS`에 행을 추가한다.
   ```js
   { key: 'carbohydrate', label: '탄수화물', unit: 'g', higherIsBetter: false },
   ```
   - **key는 `'carbohydrates'`가 아니라 `'carbohydrate'`를 사용한다.** 모달은 `item.nutrition[key]`로 값을 읽고, 백엔드 `comparison_report.py`가 내려주는 키가 `carbohydrate`이기 때문이다.
   - `higherIsBetter`는 요청대로 `false`로 둔다(탄수화물은 낮을수록 좋은 항목으로 강조).
2. 백엔드 연동 점검
   - 비교 리포트 생성 시 `carbohydrate` 값이 `nutrition`에 실제로 들어가는지 확인한다.
   - 저장된 비교 기록(`comparison_model.py` 상세 조회)을 열었을 때도 탄수화물 값이 나오는지 확인한다.
   - 값이 `null`인 경우 `_num`에서 `0`으로 처리되는지, 모달에서 `formatNumber`로 정상 표시되는지 확인한다.
3. 기존 비교 기록(이미 저장된 데이터)도 탄수화물 값이 있는지 DB에서 확인한다.

### 확인 항목
- 비교 결과 모달에 "탄수화물 / g" 행이 표시됨
- 두 개 이상 상품 비교 시 탄수화물이 가장 낮은 상품이 강조됨
- 과거 비교 기록 상세에서도 탄수화물 값이 표시됨
