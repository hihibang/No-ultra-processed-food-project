## 0. 전제 및 확인 사항

- **위시리스트 DB 연동**: 작업계획8에서 백엔드/프론트 구현이 끝났으므로 이번 작업은 확인만 한다.
- **페이지 파일명 차이** (요구사항과 실제 코드):
  - 메인: `front/src/pages/Home.jsx` → 실제 파일은 `front/src/pages/HomePage.jsx`
  - 상품 목록: `Catalog.jsx` → 실제 파일은 `front/src/pages/CatalogPage.jsx`
  - 라우트: 요구사항의 `/products?category=...` → **결정: 기존 `/catalog?category=...` 사용** (라우트 신설 없음)
- **`upf_classifier.classify_food()` 반환값** (`server/utils/upf_classifier.py`):
  `novaGroup`, `statusText`, `badgeColor`, `upfScore`, `detectedMarkers`, `nutritionWarnings`, `isUPF`
  - 확인 필요: `nutritionWarnings`의 문자열 형식. 고당류/고나트륨/고포화지방을 어떤 문자열로 담는지 확인해야 감점 대상을 판별할 수 있다. 판별 기준이 문자열 매칭이면 상수로 분리한다.
- **최신 등록 기준 날짜**: `food_product`에는 `report_date`(DATE)와 `change_date`(VARCHAR(8), YYYYMMDD)가 있다. `active_food_catalog` 뷰에 `latest_date`가 있으므로 이를 정렬 기준으로 쓴다. 확인 필요: 뷰/테이블에 `latest_date`가 실제로 포함되어 있는지 확인한다.
- **`comparison_logs` 스키마**: 현재 `comparison_id`, `user_id`, `product_ids`, `created_at`만 있다. **결정: `report JSON NULL` 컬럼을 추가**하여 리포트를 저장한다 (2-1 참고).
- **건강 점수 노출 범위**: **결정: 비교 결과 화면(결과 다시보기 모달)에만 노출**한다. 검색/목록 카드 API와 응답에는 `healthScore`를 넣지 않는다.

## 1. 백엔드 — 건강 점수 계산 (`server/utils/`)

### 1-1. 점수 산출 로직 (신규 `utils/health_score.py`)
- [ ] `calculate_health_score(classified: dict) -> dict` 구현
  - 공식: `Health Score = max(0, 100 - NOVA감점 - upfScore × 5 - 영양경고감점)`
  - NOVA 감점: 1등급 0, 2등급 -10, 3등급 -25, 4등급 -45
  - 영양경고 감점: 고당류 -10, 고나트륨 -10, 고포화지방 -5 (해당 경고가 있을 때만 적용)
  - 반환: `{ score, novaDeduction, upfDeduction, nutritionDeduction, appliedWarnings }` (감점 내역을 함께 반환해 결과 화면에서 설명 가능하게 함)
- [ ] 상수(감점 표)는 모듈 상단에 분리
- [ ] 단위 테스트: NOVA 1/4 경계값, 점수 0 하한 클램프, 경고 조합별 감점

### 1-2. 식품 영양성분 일괄 조회 헬퍼
- [ ] `FoodModel`(또는 신규 헬퍼)에서 `report_no` 목록의 영양성분을 한 번에 조회하는 함수 추가 (비교 실행 시 사용)
  - `classify_food()`에 필요한 필드(product_type, product_name, raw_materials, sugars, sodium, saturated_fat 등)를 함께 조회
- [ ] `/api/foods/search` 및 `/api/foods/recent` 응답에는 `healthScore`를 추가하지 않는다 (결정 3)

## 2. 백엔드 — 비교 API (`routes/comparison_routes.py`, `models/comparison_model.py`)

### 2-1. 저장 스키마
- [ ] `comparison_logs`에 리포트 JSON 컬럼 추가: `ALTER TABLE comparison_logs ADD COLUMN report JSON NULL`
  - 기존 로그는 `report`가 NULL이므로 상세 조회 시 재계산 경로로 처리 (2-4)
  - 마이그레이션 SQL을 `server/food_db.sql` 또는 별도 마이그레이션 파일에 기록

### 2-2. `POST /api/comparisons` 확장
- [ ] 각 `product_id`(report_no)에 대해 영양성분 + `classify_food()` + 건강 점수를 계산
- [ ] 비교 리포트 JSON 구성:
  ```
  {
    "items": [
      {
        "reportNo", "productName", "companyName", "imageUrl",
        "novaGroup", "statusText", "healthScore", "scoreBreakdown",
        "nutrition": { calories, sugars, sodium, saturatedFat, protein, ... }
      }
    ],
    "generatedAt": "..."
  }
  ```
- [ ] 리포트를 `comparison_logs.report`에 저장하고, 응답에도 동일 데이터 포함
- [ ] 기존 응답 필드(`comparison_id`, `user_id`, `product_ids`, `foods`, `created_at`) 유지 (하위 호환)

### 2-3. `GET /api/comparisons` (기존)
- [ ] 목록 응답 형태는 현재와 동일하게 유지 (`healthScore`, 리포트 미포함). 마이페이지 목록 카드에는 점수를 노출하지 않는다 (결정 3).

### 2-4. `GET /api/comparisons/{comparison_id}` (신규)
- [ ] 본인 소유 로그만 조회 가능 (다른 사용자 로그는 404)
- [ ] `report`가 있으면 저장된 리포트를 그대로 반환
- [ ] `report`가 없는 과거 로그는 `product_ids`로 현재 데이터를 기준으로 재계산하여 반환하고, 응답에 `isRecalculated: true` 표시
- [ ] 라우트 등록 순서 확인: `/api/comparisons`의 POST/GET과 충돌 없도록 path 파라미터 라우트를 마지막에 둔다
